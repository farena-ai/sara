## Recent owner cues and source-qualified follow-ups (E2 development)

New nullable messages.owner_origin and memories.origin distinguish trusted runtime/owner additions
from generic/imported/legacy rows; JSON import cannot mint provenance. conversations.dialogue_epoch
is a conservative mutation witness for actual dialogue content/role/conversation/metadata edits and
deletions, excluding inserts/no-ops/tool notices. It is not an authorization or mood field.

The pure attunement parser and read-only owner-evidence/cue adapters use current scope, quote,
category and chronology before bounded source limits. Normal chat resolves transient extras after
awaited preparation; RunRecorder refreshes final input metadata without duplicating a step or
rerunning hooks. Replay omits newly generated transient extras and propagates non-identical input
identity while keeping the original audit inspectable. General historical snapshots are unchanged.

Life revalidates every injected date and opt-out after generation, preserving usage on a dropped
result. Agenda records nullable sent epoch, answer ID/match kind and actual event date separately
from movable dueAt; automatic closure revalidates source/question/answer and never causes redelivery.
Unsupported but source-qualified plans keep normal delivery/manual authority. See
[Recent cues and follow-ups](ATTUNEMENT.md) for user controls and retention limits.

## Optional business profile (B1, 2.64.0)

`src/main.ts` dispatches `SARA_PROFILE=business` before personal authentication, stores, tools or
workers are constructed. `src/business/profile.ts` validates an independent marked root and origin;
`identity.ts` stores UUID/epoch identities and credential references in `business/business.db`,
with identity-scoped authentication files. `runtime.ts` exposes only explicitly supported business
HTTP routes; personal, household, device/API and integration entry paths never fall back to owner
authority. Passkeys are origin/identity/epoch bound. Workspace/content/recovery modules follow as
separate reviewed slices. See [Business workspaces](BUSINESS.md); no conversion of personal data.

`src/business/check.ts` supplies the argument-free `--business-check` configuration report before
profile initialization. It inspects bounded recognized metadata and descriptor-bounded profile/policy
JSON, revalidating original directory identities and canonical ancestry around reads and final output.
It never constructs SQLite, Vault or runtime objects, acquires a writer fence, or reads credentials or
content. Access/usage/recovery/credential/inference/custody/availability remain unverified.
`model-policy.ts` holds the unchanged pure policy validator shared with `model-config.ts`;
`cli.ts` rejects unknown commands and invalid command shapes before opening a profile.

`src/business/store.ts` adds organization membership, workspace registry/membership and hashed
single-use invitations to the same control database. `policy.ts` checks live browser expiry/session,
identity/organization state and explicit workspace capability; immutable issued contexts carry
all relevant revisions and must be revalidated across asynchronous boundaries. `routes.ts` is the
management/invitation router, with actor identity taken only from the business session. A manager
grants workspace access to existing active organization users; only org-admin invitations create
organization identities. `BusinessControlStore.transaction` is synchronous/non-nested and emits
fixed best-effort event metadata after commit. Durable audit now participates in the authoritative
control/content transactions separately; the event hook itself is not durable evidence.

The scoped invitation inventory uses current organization-admin or workspace-manager authority,
with the SQL scope predicate before a rowid-descending LIMIT100. Listing exposes only safe metadata
and currently visible labels, never code/hash material. A shared side-effect-free eligibility check
keeps preview, redemption and pending classification consistent with issuer revisions/authentication
epochs, subject state and existing-membership conflicts. Accepted history precedes later code
revocation; it is not a claim of current membership. The browser refreshes keyed invitation rows
independently of unsaved forms and volatile creation codes, guarded by the current view/session.

`workspaces.ts` provides per-operation business content SQLite connections at
`business/workspaces/<uuid>/content.db`; each database must contain the matching business/workspace
scope marker. Readers expose readonly DTOs, never a path, database or owner app. `retrieval.ts`
rechecks live context after awaited work; `content-routes.ts` rechecks again before HTTP output.
No shared content cache exists. `events.ts` authorizes fixed metadata SSE, bounds connections and
invalidates logout/expiry/membership changes. Runtime closes streams before draining HTTP and the
control connection. Model calls and content mutations are separate admission-controlled work.

`chat.ts`, `documents.ts` and `write-routes.ts` add scoped shared writes without constructing the
personal turn engine. `model-config.ts` loads explicit operator policy and a separate business
Vault; `budget.ts` reserves integer nanoUSD lifetime exposure transactionally in the control DB.
Client UUIDs bind actor/workspace/conversation/canonical payload; unfinished calls become held on
restart and cannot regenerate. Model context uses a scoped latest20 query, independent of the
oldest200 HTTP history page. Per-session AI disclosure and destination acknowledgement precede
inference. Provider output is buffered, bounded, live-authorized and safety-checked before commit.
Optional provider request flags enable strict usage, raw-response limits and refused redirects;
personal callers retain their existing defaults. Control and content commits are separate SQLite
transactions: interruption holds uncertainty, without claiming cross-database power-loss atomicity.
`lifecycle.ts` adds admission/drain and an exclusive local-SQLite writer fence. `audit.ts` commits
fixed metadata in control/content transactions; filesystem auth/config changes record conservative
intents. Business `backup.ts` snapshots every registry DB and key/auth material under a closed
barrier; `backup-worker.ts` validates, packages and encrypts the immutable generation. `recovery.ts`
keeps restored grants, sessions and spending closed until explicit operator reconciliation and
fresh individual passkeys. `cli.ts` dispatches offline operations before personal initialization;
personal restore rejects the business archive before touching its target. The business browser is
implemented; final integration/platform/full qualification is recorded separately. See
[Business workspaces](BUSINESS.md) and the [operator handbook](BUSINESS_OPERATIONS.md).

`static.ts` serves an explicit fixed business HTML/JS/CSS/locale allowlist, independent of the
personal app. Business modules separate authentication, translation, scoped draft state, content
and membership/audit views. A safe `me` DTO supplies current identity/role/readiness; organization
labels use a preserving audit migration. Browser requests carry an optional expected-session
consistency header checked against the cookie-derived principal, and never supply authority.
Recent-history and request-state GETs are bounded and live-authorized; status checks cannot invoke
a model, reserve budget or regenerate work. Browser draft/request bindings remain actor/session/workspace/conversation
scoped, with loaded-editor and stale-completion guards. Dispatch intent persists before network
work; only an exact live first-attempt refusal can release its immutable request binding. Actual virtual-passkey
browser journeys supplement direct API tests; physical devices/screen readers remain separate.

`scripts/qualify-business-operations.mjs` is a manual source-checkout evidence runner, not a runtime
service or scheduled check. It creates an exclusive new output directory, composes the fixed B2/B3/
onboarding browser drivers and `test/fixtures/business-operations.ts`, and retains exact child exit,
stdout/stderr and original JSON receipt digests. Partial/failed reports remain false; later children
still run after a failure. The operator fixture uses only dedicated synthetic roots to prove actual
CLI no-write behavior, scoped denials and fresh-target closed encrypted restore. Native packages,
built images and human/production acceptance retain separate gates. Docker COPY includes LICENSE;
the recipe-materialization contract complements actual release-image byte verification.

## Three words that look alike

- **Instance:** a second Sara process on the same host (`--instance NAME`, own user, port and data;
  `sudo sara instances`). See docs/INSTALL.md.
- **Server:** an address the apps keep in their list and switch between ("Your Saras"). See docs/SERVERS.md.
- **Space:** one person's data folder inside one instance (household mode). See docs/HOUSEHOLD.md.

## Q1 quality changes (2.61.4)

Q1 UI quality slice: `web/sidebar.js` owns responsive drawer inert/focus/keyboard behavior;
`web/setup-wizard.js` exposes a model-only recovery entry using the existing model step.

## Error shapes (on purpose)

- `/api/*`: `{ error, errorKey?, params?, ownerOnly? }`; `error` is English and also the translation key.
- `/v1/*`: the OpenAI shape `{ error: { message, type, param, code } }`, so OpenAI clients understand it.
- `/mcp`: JSON-RPC errors, as the MCP protocol requires.
Don't unify them.

## Principles

1. **One owner per server.** Sara belongs to one person. She can also take part in other spaces
   (Discord servers, Telegram groups) as a clearly labelled bot account, acting for her owner.
2. **Bring your own models.** Nothing is bundled; every credential is added by the owner and stored
   encrypted. Local models (Ollama, vLLM, llama.cpp) are first-class.
3. **No build step, zero runtime dependencies.** Node 24 runs TypeScript directly; the runtime uses only
   Node built-ins (`node:http`, `node:sqlite`, `node:crypto`). That keeps installs simple and the
   supply-chain surface small.
4. **Safety layer outside the model.** Disclosure, crisis handling and the minor-content block run
   in code before and after the model call, so they hold no matter which model is used.

## Linux desktop hands (CU8 draft)

Linux device code is isolated under `desktop/linux/`, outside the server's `src/` network boundary:
`cli.ts` owns local opt-ins, browser-code pairing, terminal consent/Stop and token renewal storage;
`hands.ts` specializes the shared `HandsRef` protocol/browser/tunnel engine with a production
profile, persistent Linux vault and read-only `checkup.ts` backend. No fixture desktop, fixture system
or in-memory test vault is selected by the Linux entry point. `deploy/sara` dispatches `hands` as
the current desktop user before reading server environment values; the installer copies these modules.

`dbus.ts` is a bounded, from-scratch Unix-socket EXTERNAL-authentication D-Bus codec/client (no addons,
no TCP/fd passing). It handles message framing, signatures, variants, arrays, dictionaries, calls,
errors and signals, and can host tiny TypeScript test services. `secrets.ts` uses the Secret Service
plain local-bus session and default collection, or explicit-warning private-file fallback. Backend
write failures propagate rather than acknowledging a silently lost save.

`portals.ts` implements Screenshot's Request/Response pattern, subscribing before the call and
binding replies to the unique portal owner and request path. It rejects cancelled responses and
non-local screenshot URIs. `atspi.ts` discovers the accessibility bus and performs bounded read-only
Accessible traversal, refusing secure and blocked subtrees before reading names/children. These
adapters are transport foundations, **not advertised production desktop ops**: compositor-safe
window geometry/redaction, RemoteDesktop consent/input, global Stop and native takeover are absent.
Raw portal pixels never leave the device. The shipped capability set is browser-only plus optional
`s.check`; `s.apply` is absent and every check-up suggestion is a guide.

Pairing adds a `hands` request type to the existing in-memory device-code flow. `/device` and the
Settings request row label computer control, require signed-in browser identity proof, and mint only
`hands` credentials, never general API credentials. Member/demo restrictions remain. Nested
`confirmation` separates the device code from the authenticator code (the old flat token proof
remains accepted). Existing device-code app tokens still cannot mint or manage hands credentials.

`HandsRef` now accepts a structural read-only system backend and an optional serial browser queue,
checks cancellation immediately before input/CDP and mutating page-agent calls, and rechecks consent
before saving after an abort. The fixed shared agent provides Linux owner-event observation and
local pixel redaction. Linux uses session/event matching for injected events; it does not provide a native
OS-wide input hook. Picture masks cover recognized secret fields, key-shaped text and embedded frames after capture
in a detached device-owned canvas. Authored shadow trees and oversized or changing pages refuse
pictures rather than sending uncertain pixels. Arbitrary sensitive canvas content remains opaque. See `desktop.md` and the CU8 as-built record for exact limitations and qualification.
