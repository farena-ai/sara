# Architecture

![How Sara fits together: apps and bridges, the server and its turn engine, the safety layer, models, tools and your data](architecture.svg)

To add tools, bridges, characters, MCP servers, languages or starter templates, see
[EXTENDING.md](EXTENDING.md) and the working examples in [`examples/`](../examples/).

The original sketch from the first phase:

```
┌──────────────── Interfaces ────────────────┐
│ Web UI (now) · CLI · Discord · Telegram ·    │
│ voice calls (WebRTC) · mobile (later)        │
└──────────────────────┬──────────────────────┘
               ┌───────▼────────┐
               │   Core daemon   │  HTTP API, auth, turn engine,
               │  (src/server)   │  scheduler + event bus (Phase 2+)
               └─┬─────┬─────┬──┬┘
                 │     │     │  │
          Providers  Tools  Memory  Persona + safety
```

## Three words that look alike

- **Instance:** a second Sara process on the same host (`--instance NAME`, own user, port and data;
  `sudo sara instances`). See docs/INSTALL.md.
- **Server:** an address the apps keep in their list and switch between ("Your Saras"). See docs/SERVERS.md.
- **Space:** one person's data folder inside one instance (household mode). See docs/HOUSEHOLD.md.

## Error shapes (on purpose)

- `/api/*`: `{ error, errorKey?, params?, ownerOnly? }`; `error` is English and also the translation key.
- `/v1/*`: the OpenAI shape `{ error: { message, type, param, code } }`, so OpenAI clients understand it.
- `/mcp`: JSON-RPC errors, as the MCP protocol requires.
Don't unify them.

## Principles

1. **One owner per server.** Sara belongs to one person. She can also take part in other spaces
   (Discord servers, Telegram groups) as a clearly labelled bot account, acting for her owner.
2. **Bring your own models.** Nothing is bundled; every credential is added by the owner and stored
   encrypted. Local models (Ollama, vLLM, llama.cpp) are first-class.
3. **No build step, zero runtime dependencies.** Node 24 runs TypeScript directly; the runtime uses only
   Node built-ins (`node:http`, `node:sqlite`, `node:crypto`). That keeps installs simple and the
   supply-chain surface small.
4. **Safety layer outside the model.** Disclosure, crisis handling and the minor-content block run
   in code before and after the model call, so they hold no matter which model is used.

## Provider layer

`Provider` = `listModels()` + `stream(request)`, streaming `text`, `tool_call` and `usage` events.
Conversations can pin a provider and model; otherwise the owner's default is used. Built on that:

- tool calling and vision (pictures go to the "Looking at pictures" model);
- a model for each job (Settings → Models → Which model does what) with backups if one fails, and
  **private conversations** that can only use providers on the owner's own hardware;
- **subscriptions**: Sign in with ChatGPT (`src/subscriptions/chatgpt.ts`, `src/providers/chatgpt.ts`),
  and Claude Pro/Max and SuperGrok through the providers' own official programs (Claude Code with a
  `claude setup-token` token, the Grok CLI), run as models by `src/providers/cli-agent.ts`. They use
  the owner's own plan under that provider's terms (docs/DISCLOSURES.md).

## Data

Everything lives in `SARA_DATA` (`/var/lib/sara` native, the `sara-data` volume in Docker,
`C:\ProgramData\Sara` or `%LOCALAPPDATA%\Sara\data` on Windows, `~/Library/Application
Support/Sara` on a Mac): `sara.db` (SQLite), `settings.json`, `persona.json`, `secrets.enc`,
`master.key`, `owner.json`, `library/`, `uploads/`, `workspaces/`, `companions/`, `cache/codemap`,
`logs/` and `backups/`.

**Household mode (Phase 71).** Each extra person the owner invites gets a whole data folder of their
own, `members/<id>/`, laid out like the owner's (their own `owner.json`, `sara.db`, `settings.json`,
`persona.json`, `companions/`, `library/`, `uploads/`, devices, API keys, push registrations), built
by the same code that builds the owner's space. `src/main.ts` keeps one *space* per person; the
front router resolves the person first (the `sara_m.<id>.` token prefix, or which space's session
cookie verifies), then the companion inside that space, and the request only ever reaches that
space's server instance, stores and event hub. There is no shared table with a person column to
forget to filter on. Members reach a fixed allowlist of route families (`memberRouteCheck`); the
owner's tools, server settings, backups, updates, logs, bridges and keys are not in it. With no
members nothing changes: no `household.json`, no `members/` folder, the owner's data stays where it
was. See [HOUSEHOLD.md](HOUSEHOLD.md) and THREAT_MODEL.md § Household mode.

`sara backup` (or the daily automatic backup) makes a consistent copy while she runs: each
database is snapshotted with SQLite's `VACUUM INTO`, then everything goes into one `.tar.gz`.
Meaning search keeps its vectors in the same SQLite databases and searches them in Sara's own code
(no `sqlite-vec` or other extension), so a single-user install needs no external database.

## Linux desktop hands (CU8 draft)

Linux device code is isolated under `desktop/linux/`, outside the server's `src/` network boundary:
`cli.ts` owns local opt-ins, browser-code pairing, terminal consent/Stop and token renewal storage;
`hands.ts` specializes the shared `HandsRef` protocol/browser/tunnel engine with a production
profile, persistent Linux vault and read-only `checkup.ts` backend. No fixture desktop, fixture system
or in-memory test vault is selected by the Linux entry point. `deploy/sara` dispatches `hands` as
the current desktop user before reading server environment values; the installer copies these modules.

`dbus.ts` is a bounded, from-scratch Unix-socket EXTERNAL-authentication D-Bus codec/client (no addons,
no TCP/fd passing). It handles message framing, signatures, variants, arrays, dictionaries, calls,
errors and signals, and can host tiny TypeScript test services. `secrets.ts` uses the Secret Service
plain local-bus session and default collection, or explicit-warning private-file fallback. Backend
write failures propagate rather than acknowledging a silently lost save.

`portals.ts` implements Screenshot's Request/Response pattern, subscribing before the call and
binding replies to the unique portal owner and request path. It rejects cancelled responses and
non-local screenshot URIs. `atspi.ts` discovers the accessibility bus and performs bounded read-only
Accessible traversal, refusing secure and blocked subtrees before reading names/children. These
adapters are transport foundations, **not advertised production desktop ops**: compositor-safe
window geometry/redaction, RemoteDesktop consent/input, global Stop and native takeover are absent.

Pairing adds a `hands` request type to the existing in-memory device-code flow. `/device` and the
Settings request row label computer control, require signed-in browser identity proof, and mint only
`hands` credentials, never general API credentials. Member/demo restrictions remain. Nested
`confirmation` separates the device code from the authenticator code (the old flat token proof
remains accepted). Existing device-code app tokens still cannot mint or manage hands credentials.

`HandsRef` now accepts a structural read-only system backend and an optional serial browser queue,
checks cancellation immediately before input/CDP and mutating page-agent calls, and rechecks consent
before saving after an abort. The fixed shared agent provides Linux owner-event observation and
local pixel redaction. Linux uses session/event matching for injected events; it does not provide a native
OS-wide input hook. Picture masks cover recognized secret fields, key-shaped text and embedded frames after capture
in a detached device-owned canvas. Authored shadow trees and oversized or changing pages refuse
pictures rather than sending uncertain pixels. Arbitrary sensitive canvas content remains opaque. See `desktop.md` and the CU8 as-built record for exact limitations and qualification.
